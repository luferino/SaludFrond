# Contextual clinical list filters

Clinical filters are GET-only controls in the selected patient/context. They do not create a global inbox or alter mutation forms. Assignment filters, selected assignment, and page coordinates remain separate and are retained when applying filters.

Kinesiology evaluation lists accept visible status (`draft`, `submitted`, `validated`) and inclusive UTC `date_from` / `date_to`. Evolution lists use the same filters and additionally accept a positive BIGINT decimal-string `evaluation_id`. Dates are real `YYYY-MM-DD` values in years 0001–9999; year 0000, impossible dates, duplicate/structured values, and reversed ranges are rejected before clinical reads. Backend projection remains authoritative for visible status and timestamps.

Student initial-evaluation drafts remain origin-scoped. Submitted/validated snapshots continue to use the existing patient-only cross-origin reader, which excludes drafts; no origin filter is added to that request. Student evolution reads likewise use the patient from the selected active assignment without subject/group origin filters, so the backend can return its authorized cross-context evolution snapshots. The backend remains responsible for assignment, habilitation, career, and visibility authorization; frontend tests only prove that authorized response data is rendered and do not establish backend access enforcement. An actor with origin-read access may see their authorized drafts, while a cross-context reader without that origin receives only the backend's latest submitted/validated snapshots, never live draft content. Teacher origin callers retain their full patient/subject/group request unchanged. A separate **De otros contextos** section uses patient-only reads, excludes the selected origin and drafts, and shows origin subject/group, visible status and date. Catalog names are resolved across pages; unavailable names fall back to their authoritative IDs. These labels never grant access. Cross-context read failures have their own alerts and do not hide origin lists. Evaluation links use `/teacher-clinical/other-contexts/:id`, an action-free route that checks the patient and different origin and renders only the latest immutable submission with `SubmissionSnapshot` in cross-context mode, never live detail content (including when the teacher also has origin access elsewhere). It makes no consent or correction-history request and exposes no consent, validation, correction or editing controls. Denied/missing details share the same unavailable message. Origin detail routes and actions remain unchanged. Evolutions are shown read-only only when the existing `kinesiology-evolutions:read` grant is present. An evolution read failure (other than 401, which redirects to login as before) shows an evolution-specific error inside the evolutions section and keeps the evaluation lists rendered. An invalid clinical or evolution filter is the only failure shown as a filter alert: it is caught before any clinical read, shows the parser's own message once, and keeps the filter form editable, while any other load failure shows the generic safe message without the filter form.

Oral Surgery lists accept only date bounds and always use the selected patient/context in these screens. Discovery, forbidden, and failure behavior remains unchanged. Omitted filters preserve the previous adapter requests and ordering.

Applied clinical filters carry through detail pages. Teacher and student list-to-detail links, the «Volver» links of the five detail pages, detail action URLs and their success redirects keep `status`, `date_from`, `date_to` and `evaluation_id` under those plain names, beside the existing `list_*` coordinates and `assignment_id`. Filters never enter form bodies or action schemas. `clinicalFilterCarrier` in `src/pods/kinesiology-evolution/listing.ts` applies the `parseEvolutionListFilters` rules: if any filter is invalid, duplicated or reversed, the whole set is dropped, so the URL carries nothing and no detail page fails. Without filters every URL is unchanged, except that the teacher origin redirect now keeps a valid `assignment_id`.

Validation is local synthetic frontend evidence only. It does not establish live backend, database, or production behavior.
